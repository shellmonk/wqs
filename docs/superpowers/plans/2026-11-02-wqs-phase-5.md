# WQS Phase 5 — Source Contract + Levels 1–2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Conform WQS to the real source contract and API contract (spec §4.1) — real stream decoder, string product/type dimensions, list filters, the `/wallet-data/rest/v1/projection` API — and serve aggregation levels 1 and 2 with exact totals and exact pages.

**Architecture:** A V10 migration rekeys every product dimension from `int productId` to strings (`productId`, `productType`), adds a data-driven `"wqTxType"` code table, and rebuilds the counters with a `(productType, typeId)` pair of dimensions, each with an ALL sentinel. Because the phase-2–4 decoder rejects every real message, no real projection data can exist yet: V10 truncates the projection and resets the stream offset so the corrected decoder re-ingests from the stream start. Levels 1–2 reuse the phase-4 range decomposition and counter-assisted offset over the high-level page index (page unit HIGH_LEVEL), then assemble each page with bounded indexed fetches.

**Tech Stack:** Java 21, Spring Boot 3.4.1 MVC, jOOQ 3.19.16, Flyway, MapStruct 1.6.3, Micrometer, jqwik 1.9.2 + jqwik-spring, ArchUnit 1.3.0, Testcontainers (Postgres 16, RabbitMQ), RabbitMQ stream client 0.18.0.

**Spec:** `docs/superpowers/specs/2026-10-31-wallet-query-service-design.md` — **§4.1 (binding for this phase)**, §5.5–5.7, §7.1–7.9, §8.1 (P-2..P-8), §8.5, §9. References: `docs/reference/api-contract.md`, `docs/reference/stream-message-samples.md`, `docs/reference/source-schema.sql`. Phase-4 rulings: "Execution notes" in `docs/superpowers/plans/2026-11-02-wqs-phase-4.md`.

## Global Constraints

- §4.1 is binding: where it conflicts with older spec text (§7.2 productId views, §7.8 envelope, `page`), §4.1 wins, and Task 10 rewrites the older text.
- `pageNumber` is **1-based**; `pagesAvailable == ceil(totalRowCount / pageSize)`, `0` when `totalRowCount == 0`; a page beyond the last returns 200 with empty `data`.
- Range is half-open `[from, to)`, UTC, clamped to `wqs.domain.DataDomain` (phase 4, unchanged).
- Total order at level 0: `"occurredAt" desc, "itemId" desc`. At levels 1–2: `"occurredAt" desc, "kind" desc, "refId" desc` (the high-level PK backwards).
- Sentinels: `"productType" = ''` means ALL product types; `"typeId" = 0` means ALL transaction types. `''` is unreachable from input (every blank is normalised to null at the domain boundary), and real `"wqTxType"` ids start at 1.
- An empty or absent `productTypes` / `transactionTypes` list means "no filter". A non-empty list that matches no known value yields an empty, correct page (totals 0), not an error.
- Zero-amount items are recorded in `"wqItemLocator"` only — never in an item table, rollup, high-level row or counter (§4.1).
- `/web` must never read the user id from the request (§9). `/cc` takes it from the path variable `{playerId}`, a positive decimal long; anything else is 400.
- Existing rules still hold: jOOQ §2.2 (no plain SQL outside `@RawSqlJustified`, no jOOQ types in `api/`/`domain/`, one query class per (view, level)); MapStruct §2.3; camelCase identifiers double-quoted in DDL/raw SQL; no amounts/balances/detail in INFO logs.
- Every new guard test and ArchUnit rule must be shown able to fail (a demonstrated RED) — phases 1–4 repeatedly shipped tests that could not fail.
- Test Hikari pools stay small (writer 4, reader 2).

## Decisions made for this plan

| # | Decision | Why |
|---|---|---|
| D1 | V10 **truncates** all projection state (item tables, locator, group locator, rollups, high-level, counters, pending cancels) and **deletes `"wqStreamOffset"`** rows, so the stream re-ingests from offset 0. Dead letters are kept (they hold the rejected real messages for audit). | The old decoder could not parse a single real message, so existing rows are synthetic; rebuilding is cheaper and safer than an in-place data conversion of counters. Cost if wrong: re-ingest time on a pre-production deployment. |
| D2 | `"wqTxType"("typeId" smallint pk, "code" text unique, "direction" smallint)` seeded with every type listed in `walAccountTransactions.transactionType` (source-schema.sql). Direction: PLAY = `TT_BUY`, `BUY`, `BET`, `TT_PERIODIC_CHARGE`; WIN = `TT_PRIZE_IN`, `PRIZE`; everything else NEUTRAL. An unseen code at ingest is inserted as NEUTRAL (`on conflict do nothing`, then select) — projected, never dead-lettered. Polled-source type codes (payment types, limit types) live in the same table. | Data-driven, like `wqProduct` was. Undo/rollback types stay NEUTRAL until the user says otherwise (recorded in Execution notes). |
| D3 | `"wqProduct"` is dropped; product ids and types are stored as text on every row that had `"productId"`. eInstant = product type in `wqs.einstant.product-types` (default `[instants]`). | The contract filters by product type string, and the stream carries both strings. |
| D4 | ITEM counters fan out to **four** keys per item: `(pt,t)`, `(pt,ALL)`, `(ALL,t)`, `(ALL,ALL)`; a null product type yields only the two `ALL`-product keys. HIGH_LEVEL counters use `typeId = 0` only: `(pt,ALL)`, `(ALL,ALL)`. | transactionTypes never changes L1/L2 page counts (§4.1 (b)). |
| D5 | A counter total for lists `P`, `T` is `Σ_{p∈P'} Σ_{t∈T'} count(p,t)` with `P' = P or {''}`, `T' = T or {0}`. | Exact because each item has one product type and one type. |
| D6 | A session's `"productType"`/`"productId"` is its first item's (by `occurredAt`, like `"startedAt"`); an item whose currency differs from its existing session's is **dead-lettered** (`currency-mismatch`). | §4.1 single-currency rule (O-4). |
| D7 | eInstant item without `batchId` → dead-lettered (`einstant-unsessioned`); this is the ingest half of P-7. | §7.4: asserted at ingest. |
| D8 | Non-player owners (`userType != 1`) and zero-amount items are skipped and counted on `wqs.ingest.skipped{reason=non-player|zero-amount}`; zero-amount still writes the locator row. | §4.1. |
| D9 | Detail allowlist for stream items: `subtype`, `description`, `fromDescription`, `toDescription`, `account`, `accountContext.accountType`, `accountContext.accountNumber`, `monetary`, `references.paymentId`, `references.claimId`, `references.extTrxId`, `references.extSystemId`, `createdContext.issued`, `createdContext.channel`, `batchContext.batchEnded`, `amount.reservedAmount`, `amount.nonWithdrawableAmount`. Anything else is dropped. | §4.1 allowlist. |
| D10 | List parameters bind both `?productTypes=a&productTypes=b` and `?productTypes=a,b` (Spring's default `List<String>` conversion); each value is trimmed, blanks dropped, max 50 values per list else 400. | Bounded counter fan-in. |
| D11 | Level-1/2 nested transactions are filtered by `transactionTypes` and, when set, `excludeCancelledTransactions`; session/play totals are the stored all-or-excl variant, never recomputed for the type filter. | §4.1 (b); "no aggregate computation on read". |
| D12 | `status` is omitted from every response object. `/web` principal and `/cc` access stubs are unchanged. | §4.1 deferrals. |
