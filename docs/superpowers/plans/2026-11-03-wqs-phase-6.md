# WQS Phase 6 — Delta Poller Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Project the four mutable polled sources (payments, claimable prizes, manual adjustment requests, limits) by periodically polling `GET /wallet/delta`, applying each row as a versioned upsert, with a watermark + overlap cursor and a loud timestamp-cliff alarm.

**Architecture:** One Quartz job `deltaPoll` (`@DisallowConcurrentExecution`, clustered JobStore) calls the delta endpoint with `since = watermark − overlap`, decodes each row by its `source` field into a `ProjectionItem` plus a version timestamp, and hands the batch to the existing `ProjectionWriter` in ONE transaction that also advances the watermark. A first-seen row is inserted exactly like a stream item; a strictly newer version of a known row updates only its mutable fields (status/detail) in place; an equal version is a duplicate; an older one is ignored and counted; a newer version that changes an immutable field is dead-lettered.

**Tech Stack:** Java 21, Spring Boot 3.4.1 (`RestClient`), jOOQ 3.19.16, Flyway, Quartz (clustered JDBC JobStore), Micrometer, Testcontainers Postgres 16; WireMock or `MockRestServiceServer` for the HTTP fake.

**Spec:** `docs/superpowers/specs/2026-10-31-wallet-query-service-design.md` — §4 (polled sources are mutable; delta contract; timestamp cliff), §4.1, §6.2, §6.5 (Quartz jobs), §11 (metrics `wqs.delta.*`), O-1, O-15. Source tables: `docs/reference/source-schema.sql`.

## Global Constraints

- **Test policy (user decision):** jqwik property tests are opt-in (`@Tag("property")`) and are **never run**. Every guard is a deterministic example test; show RED before GREEN. `./gradlew clean build` must stay ~1.5 min.
- Wire format (user, 2026-11-03): `/wallet/delta` returns a JSON **array of objects with one identical structure — the union of the fields of the four tables — plus a `"source"` field** naming the table. No auth (open endpoint).
- Unknown wire details are **configuration, not code**: base URL, cursor parameter name, page limit, and the `source` value → `SourceKind` mapping (D2). The decoder is one class with golden fixtures; a real sample later changes only it, its fixtures and config.
- Owner per source (user-confirmed): payments `ownerType`/`ownerId`; claimable prizes `playerId` (player by definition); adjustment requests and limits `userType`/`userId`. Only players (type 1) are projected; others skipped and counted `wqs.ingest.skipped{reason=non-player}` — before any write, as on the stream.
- `"occurredAt"` = source `created` (never changes → never moves partitions). Version = source `updated` (`statusDate` for adjustment requests, which have no `updated`).
- Routing per `SourceKind` is unchanged: prizes → /web and /cc; payments, adjustments, limits → /cc only.
- Zero-amount hiding applies to **transactions only** (§4.1 was about transactions); polled rows are always projected.
- Existing rules hold: camelCase quoted identifiers; jOOQ only outside `@RawSqlJustified`; ArchUnit green; one sequential writer (the poller and the stream consumer each run single-threaded; they may run concurrently with each other — see D8).

| D4 | Detail allowlist per source (never card/bank/email/xml data): payments `paymentType, paymentInOut, status, statusDate, channel, subChannel, description, grossAmount, serviceCost, workflowStatus, reviewHandling, approved, verified`; prizes `status, prizeLevel, wagerAmount, onHold, holdReason, workflowStatus, claimExpiryTimestamp, prizeClaimedTimestamp, claimEndedTimestamp`; adjustments `operation, transactionType, transactionSubtype, status, statusDate, reason, approved, rejected`; limits `quantityType, limitType, period, count, gameGroup, paymentMethodType, channel, effectiveFrom, effectiveUntil, approved, reason`. | §4.1 allowlist; `walPayments` holds encrypted PII. |
| D5 | V13 adds `"versionAt" timestamptz` to `"wqItemLocator"` (null for stream items) and `"wqIngestWatermark"("source" text pk, "watermark" timestamptz not null, "updatedAt" timestamptz not null default now())`. | §4 versioned upsert; §5.1 table already named. |
| D6 | Versioned apply (in `ProjectionWriter`, same transaction): locator miss → normal insert path (+ set `versionAt`); `incoming.versionAt > stored` → **only** `"detail"` (the allowlisted map, which holds status) is updated on the item row(s) in every view table the source feeds, plus `versionAt`; equal → duplicate; older → `wqs.delta.stale` counter, no write. If the newer version differs in any immutable field (`occurredAt`, `amount`, `currency`, `type`, `productId`, `productType`, `batchId`, `subBatchId`, `userId`) → dead-letter `immutable-field-changed`, nothing written. | O-15 default: only status changes; refusing other changes loudly is safer than a silent retract/re-apply we cannot test against real data. |
| D7 | Watermark: next `since` = stored watermark − `overlap` (default 120 s); after a successful batch the watermark becomes `max(version)` of the page, committed in the same transaction as the items. Empty page → watermark unchanged. **Timestamp cliff:** a page of exactly `page-limit` rows whose min and max version are equal → increment `wqs.delta.timestampcliff`, log ERROR once per occurrence, do not advance, do not loop within the run (O-1 unresolved). A saturated page with distinct versions advances to `max(version)` and the job immediately polls again within the same run (bounded by `wqs.delta.max-pages-per-run`, default 20). | §4 hazards 1 and 2. |
| D8 | The stream consumer and the poller can run concurrently and touch disjoint sources, except shared rollups when a sessioned prize joins a stream session. Both use the same lock order already documented in `RollupUpdater` (play locator before session locator); the poller applies items one batch per transaction, sequentially. | Avoid deadlock; documented risk, tested by one concurrent test. |
| D9 | Job: `deltaPoll` registered through the existing config-driven `JobRegistrar` (`wqs.jobs.delta-poll`: `enabled` default **false**, `intervalSeconds` 5, `misfirePolicy` do-nothing). HTTP failure / non-2xx / timeout → job run fails, watermark untouched, `wqs.delta.poll.failures` counter; next fire retries. | §6.5; closed by default like the stream. |
| D10 | Metrics (pre-registered): `wqs.delta.rows.fetched` (histogram), `wqs.delta.page.saturated`, `wqs.delta.watermark.age.seconds` (gauge), `wqs.delta.timestampcliff`, `wqs.delta.stale`, `wqs.delta.poll.failures`, outcome counter `wqs.delta.rows{outcome=inserted|updated|duplicate|stale|skipped|dead-lettered}`. | §11 table. |

## Review Focus

1. **Overlap re-reads** — the same row version arriving in two consecutive polls must be a duplicate, writing nothing. Pinned in Task 3 (`overlap_reread_writes_nothing`).
2. **A status-only update to a payment** — detail changes in `"wqCcItem"`, counters/rollups/high-level untouched, and `/cc` level 0 shows the new status in `detail`. Pinned in Task 2 and Task 4.
3. **A newer version that changes the amount** — dead-lettered, original row unchanged. Pinned in Task 2.
4. **More than `page-limit` rows sharing one timestamp** — alarm fires, watermark does not advance, the run terminates. Pinned in Task 3.
5. **Wallet endpoint down / returning 500 / garbage** — no watermark movement, no partial writes, failure counted. Pinned in Task 3.
