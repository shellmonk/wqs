# Read benchmark, 2026-11-04

Run with `./gradlew benchmark` (opt-in, `src/test/java/wqs/benchmark/ReadBenchmark.java`); the full
report with query plans is written to `build/benchmark/read-benchmark.md`.

**Question:** without counter tables, do plain `COUNT(*)` totals stay fast enough?
**Answer:** yes for ordinary and busy players. A player with 1M rows over 24 months (about
1,400 a day) answers in ~0.1 s at every level, and ~0.3 s with a type filter at levels 1-2.

Fixes found by this run:
- Rows without a session were looked up by id across the whole request range: 343 ms for 43 rows
  of the 1M-row player. They are now looked up within the page's own time span (2 ms).
- The levels 1-2 type filter probed every partition once per session (484 ms); it is now one
  semi-join pass over the owner's matching rows (315 ms).

Caveat: this dataset is small (3.1M rows), so the busiest player owns a third of every partition
and the level-0 count chooses a parallel sequential scan. In a 150M-row table the same player is a
small fraction and the count uses the primary key's ("userId", "occurredAt") prefix.

Postgres 16 in a container (shared_buffers 1GB), 3110000 rows over 24 monthly partitions, 277700 sessions, 1388500 plays. Seeded in 22 s.

Times are the whole service call (page + `COUNT(*)` total), in ms: one cold run, then the median of 5 warm runs. `/cc` policy (every source).
